## 实际复现与边界

本次重新运行旧版实际 Docker 镜像，20/20 官方公开用例全部通过。随后对旧版和最新版运行同一个独立 float32/欧氏距离反例驱动：

| 检查 | 旧版 0e954 | 最新版 1349 |
| --- | --- | --- |
| `3.4028235e38`、负值，舍入后仍为有限 float32 | 错误返回 TYPE | 接受 |
| 插入 `3.4028234e38` 后，将 SELECT 输出的向量重新插入 | 错误返回 TYPE | 接受 |
| `1e-400` 下溢为零 | 错误返回 TYPE | 接受 |
| 返回的两个 L2 距离均为 1，主键分别为 1、2 | 输出 2、1 | 输出 1、2 |
| `3.4028236e38` 真溢出 | 拒绝 | 拒绝 |

这些是已复现的具体差异；旧版确实有错误，最新版已覆盖上述反例。然而我们没有隐藏输入或失败日志，不能据此声称平台一定因这些断言失败，也不能宣称最新版已通过正式准入。

最小回写反例：

```sql
CREATE TABLE t(id BIGINT PRIMARY KEY,v VECTOR(2));
INSERT INTO t VALUES(1,'[3.4028234e38,0]');
SELECT v FROM t WHERE id=1;
-- 返回 [3.4028235e38,0]，旧版随后拒绝自己的输出：
INSERT INTO t VALUES(2,'[3.4028235e38,0]');
```

## 排除旧诊断与协议歧义

0e954 已使用 JSONL 默认入口，并实现 CREATE VECTOR INDEX。两版的 `src/main.cpp`、`src/protocol/jsonl.hpp`、SQL parser 与 Dockerfile 无差异。因此“仍是 dev-tsv”“尚无向量索引”属于更早版本的历史问题，不能作为本次失败解释。

本次查询官方分支仍为 `f4d4e26653af823a7601668802f80e374ad6643c`。用户新贴题面的3.1节依然出现“不再采用此前示例中的JSON请求／响应封装”，但官方 STDIO_PROTOCOL.md 明确规定当前驱动使用JSONL；这个冲突在0e954的开发记录中已存在。我们遵循具体协议及驱动，没有改回裸SQL。

独立复核还发现公开比较器的无序浮点贪心匹配可能误判相同多重集合：actual `[[0.000009],[0.000018],[0]]` 与 expected `[[0],[0.000009],[0.000018]]`，在1e-5容差下可能报缺行。是否为正式驱动同一实现未知，不能把它认作本次根因，亦不修改数据库去迎合这个猜测。

## 计分含义和下一步

按照题目准入规则，只要正式MySQL用例有一项失败，两项排名评测就不进入计分。因此“性能不计”“Agent Prompt不计”是准入失败的连带结果，不能推出性能太差或学习材料评分为零。公开20通过不能替代隐藏正式用例通过。

当前最缺的证据是题面3.5节承诺的失败类别、必要日志，以及平台锁定的实际镜像摘要/协议与资源配置。后续正式评测应确认使用预期完整SHA；更新分支不会改变已锁定旧SHA的历史结果。Agent没有自动提测或发送联系消息。
