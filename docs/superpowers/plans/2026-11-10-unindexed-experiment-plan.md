# 无索引扫描耗时拆分与优化实验计划

**Goal:** 在已上传 `64f43d1bf56af8a19eace2ddf44bae40807e6c40` 上先测无索引阶段耗时，再验证一个由证据支持的优化，保留正确性与失败实验。

**Architecture:** 复用现有 C++ 核心基准和独立排序答案；诊断计时与正常计时分开。首先比较相同数据的索引/无索引路径，若存储遍历是显著热点，则为无索引精确 TopK 复用现有单个、最多 8 MiB、第二次扫描才构建的原始行快照。每次查询仍完整验证每行；每次非 SELECT 仍先失效快照。磁盘布局、提交同步、协议及初赛分支不变。

**Tech Stack:** C++20、Python3、D 盘专用 WSL/Docker；原运行镜像 `sha256:e1cdb1e7239b915403b846f0c78ab19a4d032e58ffc77c6aba6d05552a38bc07` 作为不可变对照。

用户已批准先拆分再实验，并持续授权自主解决常规问题。本轮不推送、不提测、不更改全局设置；在既有 D 盘独立第二轮仓库工作。

## 方案选择与约束

1. 优先测量并验证存储遍历复用：无索引当前每次走 `Store::scan_in`，有索引热路径已有快照；适合明确的单因素开关对照，代价是额外驻留内存。
2. 若校验/解码占主导，再考虑计算或分配优化；当前完整有限向量验证和内联元数据已优化，不预先假定其仍是最大热点。
3. 暂不改变距离累加顺序或引入近似剪枝：本轮的目标是相同结果下减少重复工作，未经测量不扩大变更范围。

## 根据第一轮结果扩展的迭代

用户进一步授权持续自主优化、逐轮检查弱点。先完成以下两轮，再根据正常计时及完整验证决定默认设置：

1. 初始快照主场景有效，但每三次读后更新时反复释放/分配发生退化。先修正预算为零及 probation/refused 的直接扫描路径；分离 invalidate 和 clear，以独立开关验证单个 arena 的同预算复用。失效必须立即撤销旧身份和内容可读性；错误及超限仍释放。记录包含更新的总耗时、minor faults、失效后 RSS 和真实 arena 容量。
2. 暖快照剩余成本包括每个候选向量的 Cell 分配。独立开关验证查询内 scratch 复用；仍完整校验每行，保持端序、float32 位模式及既有距离累加顺序，冷索引一致性检查保持原路径。Cell 计数真实下降，新增独立复制计时，不伪装成相同物化次数。
3. 缓冲复用与 scratch 均先运行当前 API 可编译的预期失败测试，再实施；每一轮保存失败/成功及负面实验。三模式实验轮换所有执行位置，修正单纯正反序导致中间模式位置固定的问题；保留原五轮数据并注明其限制。
4. 停止条件：这些有直接测量依据的热点处理后，完整回归通过，频繁更新退化已消除或代价明确；残余优化若需要更改完整校验、精确数值或持久化规则，先列为后续研究，不为追逐局部耗时扩大本轮风险。
