# Validated data-page buffer

Each Store optionally owns a lazily allocated fixed array of four-way sets. Entries store one4096-byte immutable page, physical page ID and recency rank0..3; the budget includes padding and set metadata. Lookup chooses page_id % set_count and searches at most four ways. A hit makes the entry most recent using bounded ranks, avoiding an overflowing timestamp. On a miss, an empty entry or the least recent entry in that set is used only after full page validation succeeds. This is set-associative LRU within each set, not a global LRU or2Q implementation.

Only packed and overflow data pages are eligible. Existing index caching and scan-local packed caching remain separately selectable. Root records are read from disk at reopen; no dirty or partially written page is admitted. Admission requires a complete read, magic, checksum, expected type and structure validation. Physical-address range and expected type are checked on every cache lookup; packed references retain format/tag/slot checks on every extraction. A SQL row decoded from storage or the raw-row snapshot is validated for structure, UTF-8 and finite vectors even when its containing page hits. The separate typed query cache described below reuses the proof from a complete validated scan instead of decoding that row again.

Successful append addresses are never reused within the Store lifetime, including rollback and savepoint restoration. An unsuccessful partial page cannot be referenced by a published working root, and is not cacheable; retry can safely overwrite only that unreachable address. Cache identity is local to one exclusively locked Store and dies at close. External mutation of a live database file remains unsupported; close/reopen revalidates changed disk content.

Reads retain owned Page/row copies so callbacks can recursively scan or mutate without dangling cache references. The data-page cache cannot change key order, exact result ties, file bytes, commit boundaries, the selected synchronization policy or format02/03 compatibility.

Data-cache statistics are independent of index-cache statistics. capacity_bytes reports the actually allocated array (zero before lazy allocation); resident_pages counts occupied entries. reset_data_cache_stats resets hits/misses/evictions only. A budget smaller than one complete set disables allocation. The low-level Store default remains 0. SQL now defaults to 4 MiB and disables the scan-local memo. The historical 16 MiB experiment and its measured 16,776,960-byte array with 4,080 page slots remain documented in [buffer-results.md](buffer-results.md); they are not measurements of the current default. Use data_cache_bytes=0 to disable the current data-page buffer. Current row strings, index/query caches, allocator/fixed object overhead, SQL work state and benchmark truth data are additional memory, not included in this page-cache budget.

## Typed and raw query snapshots

SQL separately permits at most one typed or raw query snapshot, with a shared default and hard cap of 8 MiB (`scan_snapshot_bytes`, zero disables). `typed_scan_cache=true` selects owned aligned float vectors and all BIGINT columns for eligible ascending TopK queries with no predicates or BIGINT-only predicates. Its budget includes the numeric arrays and column map; the raw fallback budget includes raw bytes and row headers. These payloads never coexist. Fixed object/allocator overhead and current query scratch are outside this budget.

The first eligible scan is probation; the second attempts construction. Every base row, including rows rejected by the construction query's filter, is validated before a complete snapshot is published. Cold indexed construction also validates index/base agreement. Warm typed queries reuse that immutable proof, filter numeric columns and compute exact distances; winner projection still fetches and validates the base row. VARCHAR predicates and other unsupported shapes use the raw or streaming path. A failed or oversized builder publishes nothing and releases its payload.

Every parsed non-SELECT invalidates both snapshot identities and row counts before binding/execution, including failed mutations and transaction commands. Same-layout allocation may be retained for later rebuilding, never as a readable old snapshot. Root/schema identity is therefore stable across reuse; snapshots are not persisted and start empty after reopening. These rules do not authorize external modification of a live database file.

With `validated_vector_kernel=true`, SQL may use an internal distance entry point whose candidates already have decoder or immutable-cache finiteness proofs. It still checks query finiteness once and candidate dimensions individually, preserving scalar double accumulation, sqrt-before-ranking and signed-key ties. Public vector APIs retain full component checks; false selects the checked reference path.

## Commit policy boundary

SQL defaults to `CommitSyncPolicy::ProcessCrash`: all new immutable page write loops complete before root publication, then the whole file is synced before success is acknowledged. This mode targets process termination while the kernel/filesystem survives; it does not order an unacknowledged root against its data across power loss or a kernel/device failure. `Ordered` retains the pre-root data sync and the post-root sync, and remains the low-level Store default. Both policies poison the database on commit I/O failure until close/reopen. Cache behavior is independent of this choice.

Current experiments and validation status are recorded in [score-first-results.md](score-first-results.md). Local time/resource differences do not establish an official performance score or rank.
