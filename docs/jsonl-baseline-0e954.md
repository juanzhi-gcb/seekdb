# 上传版 0e954ffd 的实测性能基线

测量提交：0e954ffd90c6802ecd9fae4c0ca00eb8553201dd；实际runtime镜像df51f7631fcf2e9ff44f93234eb64d0ed5132441e490e50cf5b7e8e528e87321。测量期间未改引擎。不是旧版缓存实验的外推。

10000行、128维、256字符正文；每100行自动提交，插入顺序打乱。1000次TopK10，半数查询按10个组之一过滤，每轮10次统一预热。两种条件均exact，先导入再按条件建索引，每种独立容器3轮、交替先后顺序。2CPU/2GiB、只读根目录、无网络。全部数据位于D盘专用WSL虚拟磁盘。

所有写入计时发生在建索引之前，不能把第二列当作已有索引情况下的写入成本。查询单轮无索引为6.522/6.167/6.779秒，有索引为34.911/35.521/36.131秒；有索引约慢5.45倍。

正确性：外部独立C++穷举真值，6000次计时查询、60次预热、24次ANN补充查询及6次重启检查通过。核对ID、距离、正文；数据生成和真值计算在数据库容器外，不计入其内存。请求计时覆盖JSON编码、Docker管道、SQL执行、结果输出和JSON解析；核对耗时排除。统计的是请求耗时之和，非含检查器间隔的整段时间。

资源统计从宿主读取容器cgroup的memory.peak/io.stat，避免向数据库容器启动监控子进程。设备8:48的物理读均为0：这是刚导入并预热后的Linux文件缓存场景，不是冷盘检索。没有全局drop-cache，没有修改WSL交换设置。WSL Docker不能执行swap限额，观察到swap.current=0不等于正式禁swap环境。资源计数未用正式独占设备/统一冷启动流程校准，因此不能据此计算正式E或排名分；当前也没有组织者基线T/B/M。

原始每请求延迟、资源快照与摘要：[baseline证据](../bench/results/jsonl-baseline-0e954/summary.json)，以及该目录逐轮JSON和manifest。生成器和oracle保存于bench/run_jsonl_baseline.py、bench/jsonl_oracle.cpp；其D盘本地依赖路径在脚本中明确。5.6MB原始二进制输入与全部真值留在work/jsonl-baseline-full，metadata保留输入SHA256。

弱点定位：独立2000行2维诊断中，普通扫描请求215次树分支读取，有索引变成32229次，完整行验证均2010次。此诊断开启计时插桩且规模不同，只用于解释瓶颈，不与上表拼接。下一步评审后实验同步遍历表与索引，移除每行从根查找，同时保留全行校验。磁盘平坦索引的重复向量存储成本仍然存在，不能用读取优化声称写入或空间问题已解决。
